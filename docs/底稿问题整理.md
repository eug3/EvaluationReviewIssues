# 底稿问题整理说明

> 本项目只做一件事：**把「电子底稿编制 / 送审 / 复核」时要问的问题整理出来**。不做抽取、建图、判定管线。

## 一、资料来源

| 资料 | 位置 | 贡献的问题 |
| --- | --- | --- |
| 《电子底稿编制指引（征求意见稿）》 | 根目录 .docx | 送审前置要求、管理类/财务类/非财务类/收益法/市场法操作指引 |
| 管理类底稿模板（2023修订）.xlsx | 附件2/1管理类底稿 | GL-1～GL-10 各表、**档案检查要点**、**报告及说明低级错误定义表**、**明细表低级错误定义表** |
| 操作类电子底稿目录.xlsm | 附件2/2操作类底稿 | 综合类 CZ-1～CZ-21、资产基础法各科目要求、**送审表（勾选）** |

## 三、问题为什么这样分

问题沿两条轴组织：

1. **按底稿编制与送审环节**：送审前置 → 管理类 → 综合类 → 操作类（资产基础法/收益法/市场法）→ 报告说明明细表 → 归档。
2. **按底稿类型/科目**：财务类科目问题直接落到《步骤及复核表》的逐条操作步骤（`步骤复核表.yaml`），主问题集只保留跨科目通用问题和重点科目特有问题。

2024 年处罚数据校准后补充第三条轴——**按八大基本程序**（《资产评估执业准则——资产评估程序》）：每条问题标注 `procedure` 字段（P1 明确业务基本事项 … P8 整理归集评估档案，PX 跨程序/形式规范），可与处罚主题（同样按程序聚类）直接对表。处罚频次最高的问题集中在 P6「评定估算形成结论」——参数依据缺失 262 条、成本法取值 127 条、方法选取 78 条、计算错误 78 条——原问题集在这一程序上只问「有没有表」，不问「表里的数怎么来的」。为此新增 `substance` 组（评定估算实质留痕）：参数取值来源与分析判断过程、方法适用性论证、公式与勾稽复核、成本法取值依据、报告↔底稿双向一致。

每条问题含：

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定编号（`Q-SR-001` 等），引用/勾选时不要改；扩充只追加、不重排 |
| `ask` | 问题正文 |
| `check` | 判定要点 / 依据说明（可选；处罚驱动的条目注明主题 id 与频次，可作风险权重） |
| `procedure` | 所属基本程序（P1–P8/PX，图例见 YAML 头部 `procedure_legend`） |

`步骤复核表.yaml` 中每个科目含 `subject / index（底稿索引号）/ step_count / variant_count / sources / steps[]`，`steps` 即该科目《步骤及复核表》「操作步骤与要求」列原文。

## 四、怎么用

1. **逐项勾选**：把 `底稿问题集.yaml` 按组渲染成清单（或直接读 YAML），对每项打「是 / 否 / 不适用」，`否` 即问题。
2. **定位底稿**：`index` 是底稿索引号（如 `C3-5` 应收账款），文件名应与核实表索引号一致，可直接定位。
3. **与送审表对应**：`send-review` 组对应「送审表（勾选）」的审核人四问（有没有？错在哪？缺什么？完整打勾）。
4. **与报告结构对照**：`report-errors` / `detail-errors` 是报告与明细表的低级错误清单，可作为出报告前的自检。
5. **按风险排优先级**：`处罚问题映射.yaml` 的 `hits`（处罚频次）可作条目权重；`gap=True` 主题对应的 `added_by` 条目是监管实际处罚的高发点，复核时优先问。
6. **合规红线单独管理**：处罚主题中 `redline=True`（冒签/代签、未实际参与、质控失效）属违法线索，不作常规勾选项，发现即升级处理（对应 `Q-SB-003` 等）。

## 五、复现抽取

```bash
python3 scripts/extract-step-tables.py       # 各科目步骤表 -> questions/步骤复核表.yaml（依赖 xlrd / openpyxl / pyyaml）
python3 scripts/extract-penalty-issues.py    # 处罚数据（保密源表）-> questions/处罚问题映射.yaml（脱敏后）
python3 scripts/render-yaml-docs.py          # 全部 YAML -> 同名 .md
```

`extract-step-tables.py` 逻辑：遍历操作类底稿全部 `.xls/.xlsx`，取表名含「步骤」的 sheet，抽取行首形如 `N、...` 的操作步骤，剔除表尾说明，按科目归并（同名多套取最全的一套），索引号取出现次数最多者（旧模板可能带过期索引号）。

`extract-penalty-issues.py` 逻辑：读取源表「表4.评估报告信息表」490 行的问题事实列，按「处罚文件序号+事实文本」去重（1431→1170），39 个主题词典匹配（一条事实可命中多主题，主主题按源表问题类型列锚定），按八大程序聚类；**脱敏**采用哨兵占位符架构（先替换为私有区字符、最后统一还原，防级联误替换），抹去机构/企业/人名/别名/项目名/登记编号/报告文号/股票代码，保留金额、比例与准则条款引用。源表保密：已加入 `.gitignore` 不入库，仓库内只有脱敏产物。

## 六、已知边界

- 财务类底稿按 A类/B类/C类项目并存，科目相同、步骤以最全的一套入库；`variant_count > 1` 表示存在多套模板。
- 部分科目（如使用权资产、商誉、租赁负债）索引号在不同模板间有冲突，已按出现次数取众数，个别仍需人工确认。
- 步骤表的「是 / 不适用」勾选与复核人签字，是底稿合规的一部分，问题集只记录问题文本，不代替实际签字。
- 管理类 GL-4（聘请专家）、质控会记录等视项目情况适用。
- 处罚数据非全量：源表备注说明部分处罚文件仅列前 2 项问题事实；频次反映问题种类而非报告份数。河南省 84 行中 63 条为备案系统问题（`T-XX-03`，非底稿事项），已标 `scope_out` 仅保留计数。
- 主题词典为关键词匹配，1170 条事实中 159 条未归类（样例存于映射文件 `unclassified_samples`，供词典迭代）；脱敏为规则式，已抽样审计 0 残留专名，但新数据源接入时需重跑审计。
