# 底稿本体设计思考：从「追问检索图」走向「极小闭环本体」

> 本文记录从早期 `schema/kg_schema.yaml`（报告追问取证）向「资产评估底稿领域本体」演进的最初推演，并以收益法 DCF 为例给出首个极小闭环（MVP）。
>
> **全业务类型通用架构（8 类通用核心本体 + Profile 扩展包机制）请见 [`docs/底稿本体架构设计.md`](底稿本体架构设计.md) 与 [`schema/ontology_core.md`](../schema/ontology_core.md)。**

---

## 一、为什么要从「追问图」转向「底稿本体」

早期 `docs/design.md` 与 `schema/kg_schema.yaml` 采用的是 **「报告命题（ReportClaim）→ 追问（Task）→ 底稿证据片段（EvidenceSpan）」** 的检索图谱路线。这套路线在实际推进中存在三个结构性天花板：

1. **只能看出“有或没有”，看不出“推不推得出来”**
   RAG 召回的是孤立文本块。即使报告命题和几份证据之间连上了 `SUPPORTED_BY`，也只是形式上的附件挂靠，反映不出参数来源、口径一致性与计算推导拓扑。而 `questions/处罚问题映射.md` 显示，P6 评定估算类问题占处罚总量的近一半（481 条），绝大多数出在逻辑与参数断层。
2. **报告未披露的事项无法触发追问**
   以报告命题为起点自顶向下追问时，如果报告本身遗漏了表外资产、非经营性资产调整或关键假设，追问根本不会被触发，图谱上就会呈现“沉默的空白”。
3. **缺少先验的“合格结构基准”**
   没有领域本体作为骨架，每条追问是否“充分支撑”只能依赖文字规则或模型临场判断，标准容易发散。

**视角反转：**
先用本体定义**“一个站得住脚的评估结论，在底稿中本来应该具备哪些实体、逻辑链和约束”**；再把「追问」和抽取作为往本体实例中填充数据、定位断点的手段。这样一来，“底稿够不够支持结论”就转化为**图结构完备性与约束校验问题**。

## 二、为什么先做极小闭环，而不是大而全本体

完整覆盖 `questions/步骤复核表.yaml` 的 72 个科目（736 条步骤）和全套程序极易导致模型膨胀与维护失控。更务实的策略是：

* **用 `questions/底稿问题集.yaml`（207 条）框死边界**：只建模回答复核问题所需的最小概念，不相关细节一律裁剪。
* **用 `questions/处罚问题映射.yaml` 排定优先级**：优先覆盖处罚频次最高、结构最清晰的领域。

因此，第一版选择 **收益法（DCF）的「参数—计算—结论」闭环** 作为最小试验田（对应文件：`schema/ontology_dcf_mvp.yaml` / `schema/ontology_dcf_mvp.md`）。

---

## 三、极小闭环的组成（6 类 4 边 4 规则）

1. **6 个核心类**：
   * `Engagement`（项目基准：基准日、目的、主体）
   * `ReportClaim`（报告结论与关键披露）
   * `ValuationModel`（测算底稿模型）
   * `Parameter`（6 类必查关键参数：收入增长、毛利率、资本性支出与折旧、营运资金、折现率构成、非经营性/溢余资产）
   * `SourceEvidence`（支撑资料，强制区分 `objective_external` / `historical_audited` / `client_provided`）
   * `AnalysisNote`（评估师分析判断记录）
2. **4 条核心边**：
   `ReportClaim —[DERIVED_FROM]→ ValuationModel —[USES_PARAM]→ Parameter`
   `Parameter —[SOURCED_FROM]→ SourceEvidence` / `Parameter —[JUSTIFIED_BY]→ AnalysisNote`
3. **4 条硬校验规则**：
   * `R-01` 数值双向闭合（报告值 == 模型输出值）
   * `R-02` 参数双链约束（不能仅连向委托人提供资料，必须有客观外部/历史依据或评估师分析记录，直击 `T-VA-01` 262 条最高频处罚）
   * `R-03` DCF 6 类关键要素完备性（防漏项）
   * `R-04` 基准日口径一致（防错期）

## 四、后续三步落地验证

1. **样例实例化**：挑选 1 个已完结的 DCF 案例，先不写复杂解析器，按 `schema/ontology_dcf_mvp.yaml` 手工或半自动填写一份实例 YAML。
2. **断点校验脚本**：编写轻量 Python 校验脚本，针对实例运行 `R-01 ~ R-04`，输出断链节点并自动点亮 `底稿问题集.yaml` 中对应的 `Q-*` 条目。
3. **横向扩展**：DCF 闭环跑通后，再按同样方式向「资产基础法重点科目（如应收、存货、设备）」和「程序时间线/签字合规（GL/CZ）」复制扩展。
