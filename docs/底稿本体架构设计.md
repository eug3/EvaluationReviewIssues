## 一、设计背景与核心转向

### 1.1 早期「追问检索图」的结构性局限

仓库早期方案（见 `docs/design.md` 与 `schema/kg_schema.yaml`）以**评估报告文本**为起点，采用 `报告命题（ReportClaim）→ 追问（Task）→ 底稿证据片段（EvidenceSpan）` 的 RAG 检索建图路径。该路径在面对真实底稿复核与监管处罚标准时存在三个瓶颈：

1. **只见附件挂靠，不见推导拓扑**：文本检索只能判断“底稿里有没有相关段落”，无法表达参数与模型之间的口径衔接、数据血缘以及评估师是否履行了独立分析判断。而在 `questions/处罚问题映射.md` 的 1170 条去重处罚事实中，P6「评定估算形成结论」高达 481 条，核心痛点正在于逻辑链断裂。
2. **报告沉默导致漏查**：自顶向下按报告命题触发追问时，若报告遗漏了表外无形资产（如未入账商标）、未决诉讼、非经营性资产调整或关键假设，追问根本不会被触发。
3. **缺乏先验合格基准**：没有领域本体定义“合格底稿应有的结构”，对 `supported` 与 `insufficient` 的裁定容易退化为大模型的主观自由发挥。

### 1.2 转向「先验模具本体 + 闭合世界校验」

底稿本体的核心思想是**视角反转**：

- **先定义模具（Ontology）**：先验规定一个站得住脚的评估结论，在底稿中必须具备哪些实体槽位、逻辑连线与程序留痕。
- **再填充与验伤（Instantiation & Validation）**：将早期的「追问、RAG 检索、Excel 公式核对」降维为数据采集器，把具体项目的底稿信息填入模具生成项目实例图；凡是必查槽位悬空、证据性质单一、跨载体数值或日期冲突的地方，自动暴露为断链并映射回 `questions/底稿问题集.yaml` 的具体问题编号。

## 二、总体三层架构

仓库内全部资产按职责划分为上下贯通的三层：

```

│ 1. 立法与经验层（审什么 / 风险权重）                                │

│    - questions/步骤复核表.yaml   （72 个科目 / 736 条操作步骤）     │
│    - questions/处罚问题映射.yaml （39 个处罚主题 / 风险频次与红线） │
└───────────────────────────────┬───────────────────────────────────┘
                                │ 提炼结构不变量与槽位清单
                                ▼
┌───────────────────────────────────────────────────────────────────┐
│ 2. 领域本体层（合格底稿的先验结构模具）                             │

                                │ 指导定向抽取与闭合校验
```

## 三、通用核心本体（Core Ontology：8 类 7 边）

为了同时覆盖**企业价值、单项资产、无形资产、以财务报告为目的的评估**四大业务类别，以及**收益法、市场法、资产基础法（成本法）**三大方法，通用核心层收敛为 **8 个核心类**，横跨「全局与管理链」「对象与核查链」「模型与估值链」三个子域：

### 3.1 八个核心类

| 子域 | 类名 | 中文名 | 核心职责 | 覆盖程序 |
| --- | --- | --- | --- | --- |
| 全局与管理 | `Engagement` | 项目基准 | 锚定评估目的/经济行为、评估基准日、报告日、项目属性标签（如国有资产/司法/财报目的）及参与人员角色 | P1, P2, P3 |
| 对象与核查 | `SubjectAsset` | 评估对象与科目 | 表示被评估标的（企业整体、资产组、单项不动产/设备/无形资产，或资产基础法下的 72 个具体科目），记录账面值、权属状态、表内外属性与经营/非经营属性 | P1, P4, P5 |
| 对象与核查 | `ProcedureRecord` | 程序与合规留痕 | 表示执业与质控动作记录：现场勘察、盘点监盘、独立发函/回函、原件核对签字、访谈纪要、三级审核意见及修改回复闭环 | P3, P4, P8 |
| 模型与估值 | `ValuationModel` | 测算底稿模型 | 表示具体评估方法的计算表或汇总模型（如 DCF 17 张表、市场法比较表、设备重置成本测算表、科目核实与评估汇总表） | P6 |
| 模型与估值 | `Parameter` | 关键评估参数 | 表示模型中影响结论的核心输入或调整项（如增长率、折现率、成新率、重置单价、可比修正系数、坏账计提率、溢余调整额） | P6 |
| 支撑与论证 | `SourceEvidence` | 支撑资料证据 | 表示参数、权属或账面值所依赖的底稿文件（权证、合同、审计报告、询价记录、外部数据库、盈利预测表），**强制标记证据来源独立性** | P4, P5 |
| 支撑与论证 | `AnalysisNote` | 分析判断记录 | 表示评估师的专业分析与核查验证留痕（方法适用性论证、参数与历史差异原因分析、可比案例筛选剔除理由、增减值原因分析） | P6, P7 |
| 报告与披露 | `ReportClaim` | 报告结论与披露 | 表示评估报告、评估说明、评估明细表中对外输出的结论金额、关键参数陈述、评估假设与特别事项披露 | P7 |

#### `SourceEvidence` 的来源独立性分级（核心设计点）

为精准拦截“直接采用委托人资料而无核查判断”的高频违规，所有 `SourceEvidence` 必须标记 `source_kind`：

- `external_independent`：外部独立客观证据（政府定额、公开市场交易/同花顺数据、评估机构独立询价、独立回函、知识产权局查询记录）
- `historical_audited`：经审计的历史财务数据或生效法律文书/权属原件（经评估师核对原件签字）
- `client_provided`：委托人或被评估单位单方编制的材料（如企业提供的未来盈利预测表、未审报表、情况说明）

### 3.2 七条核心语义关系

```
Engagement ──[HAS_SUBJECT]────────► SubjectAsset
SubjectAsset ──[VERIFIED_BY]──────► ProcedureRecord ──[EVIDENCED_BY]──► SourceEvidence
SubjectAsset ──[VALUED_BY]────────► ValuationModel  ──[JUSTIFIED_BY]──► AnalysisNote（方法适用性论证）
ReportClaim  ──[DERIVED_FROM]─────► ValuationModel  ──[USES_PARAM]────► Parameter
Parameter    ──[SOURCED_FROM]─────► SourceEvidence
Parameter    ──[JUSTIFIED_BY]─────► AnalysisNote    （参数取值与差异分析）
ReportClaim  ──[DISCLOSES_FOR]────► SubjectAsset    （权属瑕疵/特别事项/假设披露）
```

| 关系名 | 起点 → 终点 | 业务语义 |
| --- | --- | --- |
| `HAS_SUBJECT` | `Engagement → SubjectAsset` | 本次评估范围包含的评估对象或申报科目（含识别出的表外资产负债） |
| `VERIFIED_BY` | `SubjectAsset → ProcedureRecord` | 针对该对象/科目履行的现场勘察、盘点、函证、权属核验或审核程序 |
| `VALUED_BY` | `SubjectAsset → ValuationModel` | 该评估对象/科目所采用的测算底稿模型（可关联单一模型或两种方法模型） |
| `DERIVED_FROM` | `ReportClaim → ValuationModel` | 报告、说明或明细表中的数值与结论由哪张测算模型推导得出 |
| `USES_PARAM` | `ValuationModel → Parameter` | 测算模型使用并受其驱动的关键评估参数或调整要素 |
| `SOURCED_FROM` | `Parameter / ProcedureRecord → SourceEvidence` | 参数取值或程序核验所引用的原始证据资料（也可写作 `EVIDENCED_BY`） |
| `JUSTIFIED_BY` | `Parameter / ValuationModel → AnalysisNote` | 方法选取适用性论证，或参数取值的核查验证、调整与差异分析过程 |

## 四、五类通用校验原语（Validation Primitives）

底层校验引擎不需要理解千差万别的行业术语，只需在项目实例图上执行以下 **5 类闭合世界（Closed-World / SHACL 式）校验原语**：

### 4.1 槽位完备性原语（`SlotCompleteness`）
- **逻辑**：当项目或对象匹配某一规则包（Profile）时，规定的必查 `SubjectAsset`、`ProcedureRecord`、`Parameter`、`ReportClaim` 槽位必须存在且非空。
- **典型拦截**：
  - DCF 漏测算期末营运资金回收或溢余资产（`T-VA-08` / `Q-DCF-018`）
  - 实物资产无现场勘察记录或盘点表（`T-FI-01`、`T-FI-02` / `Q-NF-003`、`Q-FF-001`）
  - 单一评估方法未挂接方法适用性 `AnalysisNote`（`T-VA-02` / `Q-SB-002`）
  - 仅形成结论而无任何 `ValuationModel` 测算底稿（合规红线 `T-VA-07` / `Q-SB-003`）

### 4.2 参数双链防挂靠原语（`DualLinkSubstantiation`）
- **逻辑**：任何标记为关键的 `Parameter`，若其 `SOURCED_FROM` 仅指向 `source_kind = client_provided` 的证据，则必须同时具备指向 `external_independent / historical_audited` 的第二证据链，**且**具备 `JUSTIFIED_BY → AnalysisNote` 的核查分析记录；否则判为“单链悬空（形式挂靠）”。
- **典型拦截**：
  - 直接采用委托人提供的盈利预测、无外部佐证与分析判断（处罚榜首 `T-VA-01` 262 条、`T-VA-04` 49 条 / `Q-SB-001`、`Q-DCF-016`）
  - 固定资产成新率、重置单价、市场法修正系数无取值依据与计算过程（`T-VA-05` 127 条、`T-VA-06` 72 条 / `Q-SB-006`、`Q-MK-011`）

### 4.3 跨载体对齐原语（`CrossArtifactAlignment`）
- **逻辑**：校验不同节点同名/同义属性之间的相等或映射关系。
- **典型拦截**：
  - **数值双向闭合**：`ReportClaim.value == ValuationModel.output_value`（报告 ↔ 说明 ↔ 明细表 ↔ 底稿计算表一致，`T-RP-02` / `Q-SB-005`、`Q-RE-008`）
  - **基准日与区域口径对齐**：`ValuationModel.base_date == Engagement.valuation_base_date`；定额区域 == `SubjectAsset.location`；函证基准日 == 评估基准日或附替代测试（`Q-RE-010`、`Q-SB-006`、`T-DC-05`）
  - **索引闭合**：核实表索引号 == 实质性底稿文件名编号（`Q-SR-008`、`Q-FG-002`）
  - **瑕疵透传披露**：凡 `SubjectAsset` 存在权属瑕疵（抵押/查封/未办证）或账外资产特征，必须存在对应的 `ReportClaim(特别事项说明)` 节点（`T-RP-05` / `Q-RE-028`）

### 4.4 时间线单调性原语（`TimelineMonotonicity`）
- **逻辑**：校验项目生命周期关键日期的偏序关系：
  - `业务约定书签订日 ≤ 现场调查/勘察盘点日 ≤ 全部必需评估程序完成日 ≤ 评估报告日`
  - `经济行为依据文件日期 ≤ 评估报告日`
  - `评估报告日 ≤ 归档日期 ≤ 评估报告日 + 3个月（除非有延期归档申请）`
- **典型拦截**：时间倒挂低级错误与程序造假风险（`Q-RE-007`、`Q-RE-029`、`Q-AR-015`、`T-RP-06`）。

### 4.5 职责分离与签署合规原语（`RoleSegregationAndSignoff`）
- **逻辑**：校验 `ProcedureRecord` 与 `Engagement` 中的人员角色及签章布尔约束：
  - `报告签字评估师 ≠ 项目三级审核人`（`Q-MG-008`）
  - `签字评估师 ∈ 实际参与现场/核心程序人员集合`（红线 `T-XX-02`）
  - `三级审核记录.has_substantive_opinion == true && has_manager_reply == true`（拦截仅签字无实质内容，`T-AR-04` / `Q-MG-008~009`）
  - 权证/审计函证复印件必须具备评估人员“与原件核对一致”签字及日期；盘点表须三方签字盖章（`Q-SR-010~011`、`Q-FF-001`）。

## 五、扩展规则包机制（Profile：怎么查各类评估项目）

通用核心本体保持稳定不变，不同评估项目的差异全部收敛到声明式的 **Profile（规则配置包）** 中。当一个项目进入复核时，根据 `Engagement` 的业务属性自动叠加对应的 Profile：

| 规则包 ID | 适用范围 | 挂载的必查槽位（Slots）与专属约束 | 关联问题集分组 |
| --- | --- | --- | --- |
| `profile_common_gl_archive` | **全项目必选底座**（另含国资/司法/征收子开关） | GL-1~GL-10 管理类留痕、委托合同签章、针对性评估计划、三级审核实质意见闭环、初步报告归档、时间线单调性；国资附加经济行为文件与资产清查章节，司法附加法释〔2018〕15号等依据 | `send-review`、`management`、`general`、`report-errors`、`archive` |
| `profile_dcf` | **收益法项目**（企业价值 DCF、无形资产超额收益、财报减值测试） | 6 类核心参数槽位（收入/毛利、Capex与折旧匹配、营运资金及期末回收、折现率各构成、非经营性/溢余资产）；减值测试附加“资产组范围一致 + 税前折现率匹配”约束 | `dcf`、`substance`（见已落地的 `schema/ontology_dcf_mvp.yaml`） |
| `profile_market` | **市场法项目**（上市公司比较法、交易案例比较法、不动产市场法） | 初选样本池与逐家入选/剔除 `AnalysisNote`、可比公司数量 > 3 家、上市及重组后稳定运行 ≥ 3 年、剔除 ST/停牌/新三板、价值比率多维修正参数来源、同花顺断开链接表 | `market`、`substance` |
| `profile_physical_intangible` | **单项实物/无形资产 & 资产基础法非财务科目**（土地、房建、设备、存货、专利商标） | **核查侧**：权证原件核对签字、知识产权局查询记录、实地勘察表与照片、存货/固资盘点签章；**估值侧**：独立市场询价记录、定额与资产所在地匹配、成新率计算公式与年限/勘察依据 | `nonfinancial`、`financial-focus`（存货）、`detail-errors`、`substance` |
| `profile_financial_accounts` | **资产基础法财务类科目**（对应 `步骤复核表` 流动/非流动资产及负债科目） | 核实表索引号与文件名对齐；货币资金/往来/借款独立函证或审计函证原件复核签字 + 替代测试；应收账龄与坏账取证；表外负债（担保/未决诉讼/承诺）识别底稿 | `financial-general`、`financial-focus`、`步骤复核表.yaml` |

> **组合示例**：
> - 一个「国有企业股权转让评估（采用资产基础法 + 收益法）」项目，自动拼装：`profile_common_gl_archive(国资=true)` + `profile_financial_accounts` + `profile_physical_intangible` + `profile_dcf`。
> - 一个「人民法院司法执行单套商业房产评估（采用市场法 + 收益法）」项目，自动拼装：`profile_common_gl_archive(司法=true)` + `profile_physical_intangible(不动产)` + `profile_market` + `profile_dcf`。

## 六、设计边界（三进三不进）

为防止本体在迭代中失控膨胀，严格执行以下边界准则：

### 应当进入本体的内容（三进）
1. **进拓扑完备性**：某类项目/方法下不可缺席的对象、核查程序、关键参数与分析记录节点。
2. **进证据独立性与合规元数据**：证据来源分类（外部客观 / 历史审定 / 委托人提供）、签字角色、公章状态、关键业务日期。
3. **进跨载体口径对齐**：报告、说明、明细表、核实表与测算表之间的数值、基准日、索引号、权属证号一致性。

### 绝不塞入本体的内容（三不进）
1. **不进逐行算术明细**：不在本体图中把 Excel 每一行加减乘除建成成百上千个 `CalculationStep` 节点；表内公式勾稽与汇总错行由确定性 Excel 检查脚本核验后，直接向 `ValuationModel` 节点回填核验状态。
2. **不进纯排版字面检查**：错别字、目录页码跳序、页眉名称错误等（`report-errors` / `detail-errors` 中的纯文本格式项），由文档级规则检查直接处理，不污染领域本体。
3. **不替代评估师商业拍板**：本体负责把“预测增长率与历史差异大却无外部佐证、无分析说明”精准抓出来标红，但不替复核人裁定具体业务增长率取 12% 还是 15%。

## 七、分阶段演进路线

1. **阶段一：单 Profile 桌面推演（已完成初稿）**
   以 `schema/ontology_dcf_mvp.yaml` 验证「参数双链约束 + 6 类必查槽位」对 P6 高频处罚问题的表达能力。
2. **阶段二：通用核心层收敛（当前阶段）**
